## 3. Findings

### F-1 — The giver's Rock Account keeps controller rights over a rock it no longer owns {#f-1}

**Severity: High** (permanent lock of someone else's rock, no attacker precondition beyond the
system's own documented default).

**Where:** `_requireRockController` L588-L592; `claimHandover` L437-L458 (which writes
`r.currentOwner` at L453 and never touches `r.smartAccount`); `archiveRock` L364-L380.

**Narrative.** `_requireRockController` admits two addresses: `r.currentOwner` and
`r.smartAccount`. Admitting the Safe is deliberate and correct — under sponsorship the call
arrives *from* the Safe — and its NatSpec justifies it with "the Safe is controlled by the current
owner's signing key". That sentence is true at awakening and false after every handover, because
`claimHandover` changes the owner and leaves `smartAccount` at the address bound in `awakenRock`.

Whether the Safe's *own* owner follows the rock is decided off-chain, and D-027 states plainly
that for an **open** handover it never does: "an open handover cannot be pre-signed, so its
registry claim succeeds while the Safe owner swap is reported `UNAVAILABLE`". So after Alice gives
her rock openly and Bob claims it:

1. Bob is `currentOwner`. The app shows Bob as the owner and the provenance is correct.
2. Alice still owns the Safe recorded as `smartAccount`, and the Safe still satisfies
   `_requireRockController`.
3. Alice sends one transaction from that Safe — `archiveRock(rockId)`. The state becomes
   `Archived`, which is terminal by design: "an archived rock can never be awakened, given,
   claimed, flagged lost, or un-archived; there is deliberately no `unarchive`". Bob's rock is
   destroyed as a registry object, the tag binding is released, and the event log shows the
   archive as the act of a legitimate controller.

She can also `initiateHandover` Bob's rock to herself-by-proxy, `markLost` it, or churn it between
states. Nothing Bob can do reverses the archive, and nothing in the contract warns him.

The same window opens, more narrowly, for a *named* handover whenever the pre-signed owner swap
fails to land — the claim route submits it after the registry claim has already succeeded and
reports `UNAVAILABLE` if the bundler refuses (`claim/route.ts:88-97`), leaving exactly this state.

Note the second-order consequence for funds: the registry holds none, but the Safe that still
satisfies its owner gate is also the Safe holding the rock's assets. D-027 states that for the
Safe. Nothing states it for the registry, and the registry is the thing a reader consults to learn
who controls a rock.

**PoC:** `test/audit/BankRockRegistryAudit.t.sol`
`testAudit_F1_theGiversSafeCannotArchiveTheRockAfterTheHandover`,
`testAudit_F1_theGiversSafeCannotReGiftTheRockAfterTheHandover` — both fail today.

**Recommended fix.** Make the recorded Rock Account follow the owner, and say so:

```solidity
/// @param att ... `att.smartAccount` is the Rock Account the claimant will custody this rock in.
function claimHandover(uint256 rockId, address smartAccount, Attestation calldata att, bytes calldata sig)
    external whenNotPaused
{
    ...
    if (smartAccount == address(0)) revert InvalidSmartAccount();
    if (att.smartAccount != smartAccount) revert AttestationSmartAccountMismatch(att.smartAccount, smartAccount);
    ...
    r.currentOwner = att.subject;
    r.smartAccount = smartAccount;          // <- the authority follows the object
    emit RockClaimed(rockId, previousOwner, att.subject, smartAccount, att.counter);
}
```

This is also what D-029 already implies — the Rock Account is derived from *(tag, owner)*, so the
recipient's account is a different address from the giver's, and the registry is currently storing
a value D-029 says is stale the moment the owner changes. It is an ABI change to
`claimHandover`, so it must land together with the ABI export, the web encoders and the MCP copy
(Part 2.2 explicitly permits this).

If the ABI must not change, the fallback is to drop `smartAccount` from `_requireRockController`
and route sponsored owner actions through the owner's own wallet; that costs the gasless flows and
should be a conscious trade, not a default. Either way the PoC tests pass.

### F-2 — An attestation has no maximum lifetime on-chain {#f-2}

**Severity: Medium** (a long-lived bearer token; misleading on-chain documentation).

**Where:** `_consumeAttestation` L622; the contract-level NatSpec L60-L66 ("it is spent the moment
it lands"); `web/src/lib/nfc/attestation.ts:39` (`ATTESTATION_TTL_SECONDS = 600`).

**Narrative.** The registry accepts any `deadline` strictly in the future — there is no upper
bound. The ten-minute lifetime exists only in the TypeScript signer. A second signer
implementation, a bug in the clock arithmetic (`now + TTL` with `now` in milliseconds is a
five-century deadline), or an operator signing a payload by hand, all produce an attestation that
stays spendable for as long as the counter is not superseded *on-chain* — and the on-chain counter
only advances when an attestation is actually consumed, not when the tag is read. So a captured
attestation is not invalidated by later taps; it is invalidated by a later *claim*. The contract's
own threat-model note ("a URL captured from a genuine tap cannot be replayed against the chain
after the tag has been read again", L57-L59) is therefore slightly stronger than what the code
enforces.

Part 1.2 asks for the maximum lifetime to be documented on-chain. It should be enforced there too:
the cost is one comparison, and it converts a policy into an invariant.

**PoC:** `testAudit_F2_anAttestationWithAnUnboundedDeadlineIsRejected` — an attestation with
`deadline = type(uint256).max` is accepted today.

**Recommended fix.**

```solidity
/// @notice The longest an attestation may be valid for: the off-chain signer's TTL
///         (`ATTESTATION_TTL_SECONDS` in web/src/lib/nfc/attestation.ts), enforced here so a
///         signer bug cannot mint a long-lived bearer token.
uint256 public constant MAX_ATTESTATION_LIFETIME = 10 minutes;

error AttestationLifetimeTooLong(uint256 deadline, uint256 maxDeadline);
...
if (att.deadline < block.timestamp) revert AttestationExpired(att.deadline, block.timestamp);
uint256 maxDeadline = block.timestamp + MAX_ATTESTATION_LIFETIME;
if (att.deadline > maxDeadline) revert AttestationLifetimeTooLong(att.deadline, maxDeadline);
```

Also correct L57-L59 to say what is true: replay protection consumes a counter *on-chain*, so an
outstanding attestation dies when a higher counter is accepted by this contract.

### F-3 — Administration can be destroyed in one call {#f-3}

**Severity: Medium** (permanent loss of the attester rotation and the pause switch; requires an
owner mistake or an owner-key compromise).

**Where:** `import {Ownable}` L4; `Ownable(initialOwner)` L252; `setAttester` L266; `pause` L274.

**Narrative.** Two separate defects, one cause. `renounceOwnership()` is inherited, live, and sits
on the Etherscan Write tab one row from `transferOwnership` — exactly the surface Part 2 is
written to make safe. Calling it sets the owner to zero, after which `setAttester` can never be
called again. If the attester key is later lost or rotated off, every `awakenRock` and
`claimHandover` reverts `InvalidAttestationSignature` for ever: the registry becomes a read-only
monument and every live rock is frozen in its current state. That is the threat-model row "make
the attester unrotatable", reachable by one click.

Second, `transferOwnership` is single-step: a mistyped address takes the contract with it,
silently and immediately.

**PoC:** `testAudit_F3_ownershipCannotBeRenouncedOrHandedToATypo`.

**Recommended fix.** Inherit `Ownable2Step` and disable renunciation with a named error:

```solidity
import {Ownable, Ownable2Step} from "@openzeppelin/contracts/access/Ownable2Step.sol";

/// @notice Thrown by `renounceOwnership`. This registry must always have an administrator: the
///         attester has to stay rotatable, or every future tap is unusable.
error OwnershipCannotBeRenounced();

/// @notice Disabled. Use `transferOwnership` + `acceptOwnership` to move administration.
function renounceOwnership() public view override onlyOwner {
    revert OwnershipCannotBeRenounced();
}
```

### F-4 — A handover has no maximum duration {#f-4}

**Severity: Low.**

**Where:** `initiateHandover` L405.

**Narrative.** `expiresAt` need only be in the future, so `type(uint64).max` is accepted. An open
handover with no practical expiry is a standing, unrevoked offer of the physical object to whoever
next taps it — the rock is `HandoverPending` for ever, the UI shows a gift that never lands, and
the owner must remember to cancel it. Part 2.2 asks for `MAX_HANDOVER_DURATION` as a named,
`@notice`-d, tested constant; there is no constant at all.

**PoC:** `testAudit_F4_aHandoverCannotBeOpenForever`.

**Recommended fix.**

```solidity
/// @notice The longest a gift may stay claimable. A gift that has not been collected in 30 days
///         has not been collected; the owner can always open a new one.
uint64 public constant MAX_HANDOVER_DURATION = 30 days;

error HandoverTooLong(uint64 expiresAt, uint64 maxExpiresAt);
...
if (expiresAt <= block.timestamp) revert InvalidHandoverExpiry(expiresAt, uint64(block.timestamp));
uint64 maxExpiresAt = uint64(block.timestamp) + MAX_HANDOVER_DURATION;
if (expiresAt > maxExpiresAt) revert HandoverTooLong(expiresAt, maxExpiresAt);
```

### F-5 — Tokens mis-sent to the periphery are paid out to the next caller {#f-5}

**Severity: Medium** (theft of third-party funds, no privilege required; the loss requires the
victim's mistake, which is why it is not High).

**Where:** `XYCSwapTaker.sol` L99-L104.

```solidity
// Nothing is meant to stay here. Return any residue to the caller so a failed assumption
// (or a stray transfer) can never be stranded or swept by the next taker.
uint256 residue = tokenIn.balanceOf(address(this));
if (residue > 0) { tokenIn.safeTransfer(msg.sender, residue); }
```

**Narrative.** The comment states the intent exactly backwards. The refund is computed from the
contract's *whole balance*, not from what this swap pulled, so every token sitting in the
periphery for any reason is paid to the next person who happens to swap that token. The periphery
is public, unowned, and advertised in the UI as the address a visitor approves — it is precisely
the address a user will paste into a wallet's send field by mistake. An attacker watching the
mempool needs one one-wei swap to collect; on a value-bearing network this is a standing bounty on
other people's typos.

On the honest path the residue is always zero (Aqua's `push` consumes the entire `amountIn`), so
the branch buys nothing and costs a `balanceOf` on every swap.

**PoC:** `test/audit/XYCSwapTakerAudit.t.sol` `testAudit_F5_strayTokensAreNotPaidOutToTheNextCaller`.

**Recommended fix.** Decide, and write the decision into the NatSpec — Part 1.2 asks for exactly
that. The cheapest correct decision:

```solidity
// The app consumes the whole input; a residue means an assumption failed, so refund only what
// this swap pulled from this caller and never the contract's balance.
uint256 spent = balanceBefore - tokenIn.balanceOf(address(this)); // balanceBefore read after the pull
...
/// @dev Tokens transferred to this contract outside a swap are unrecoverable. It has no owner
///      and no rescue function by design: a rescue is an admin key, and this periphery exists
```

### F-6 — The app is an unvalidated caller-supplied address, and the callback believes it {#f-6}

**Severity: Medium.**

**Where:** `swapExactIn` L78 (`XYCSwap app` is a parameter), L88-L96; `xycSwapCallback`
L108-L123.

**Narrative.** The taker calls whatever address the caller names, and the callback's only check is
that the caller of the callback is that same address. Everything else the callback acts on —
`tokenIn`, `amountIn`, `maker`, `strategyHash` — comes from that address, unverified against the
swap the periphery itself started. The callback then `forceApprove`s Aqua for that amount and
pushes it.

So an arbitrary "app" can make the periphery approve and move **any token the periphery is holding
at that instant, in any amount, to any maker**, inside a swap whose own declared `amountIn` is
zero. Today the periphery holds something only transiently (the caller's own input) or by mistake
(F-5), which bounds the loss to the caller's own funds plus stray balances — which is why this is
Medium and not High. It stops being bounded the moment anything else ever rests in the contract,
and it is the mechanism that makes F-5 exploitable without even a real strategy.

Two realistic ways a user reaches this without being the attacker: the Etherscan Write tab, where
`app` is just an address field on the function Part 2 says a stranger must be able to drive; and a
compromised or mistyped `NEXT_PUBLIC_AQUA_APP_ADDRESS`, which the web app passes straight through.
`deploy-aqua-app.js` deploys exactly one app and prints its address — nothing binds the taker to
it.

**PoC:** `testAudit_F6_anArbitraryAppCannotPushTokensThePeripheryNeverPulled`.

**Recommended fix.** Both halves:

1. Record the swap in transient storage and check the callback against it, not just the caller:

```solidity
address private transient _activeApp;
address private transient _activeTokenIn;
uint256 private transient _activeAmountIn;
...
require(msg.sender == _activeApp && app == _activeApp, UnexpectedCallback(msg.sender, _activeApp));
require(tokenIn == _activeTokenIn, UnexpectedCallbackToken(tokenIn, _activeTokenIn));
require(amountIn == _activeAmountIn, UnexpectedCallbackAmount(amountIn, _activeAmountIn));
```

2. Bind the app: `IXYCSwapApp public immutable APP;` set in the constructor beside `AQUA`, and drop
   the parameter. `deploy-aqua-app.js` already deploys the app first, so it has the address to
   pass. If several apps must be supported later, an immutable pair or a constructor-fixed
   allowlist keeps the property. This also removes a field from the Etherscan form, which is a
   Part 2 win.

### F-7 — One swap admits an unlimited number of callbacks {#f-7}

**Severity: Medium.**

**Where:** `_activeApp` set L88, cleared L97 — i.e. only after `app.swapExactIn` *returns*;
`xycSwapCallback` L118-L119 reads the gate and never clears it.

**Narrative.** The gate is a window, not a ticket. For the whole duration of the app call, any
number of `xycSwapCallback` invocations succeed, each approving and pushing again. The reference
`XYCSwap` calls back exactly once, so nothing is wrong on the honest path today — which is exactly
why the checklist asks for it to be *enforced* rather than assumed. Combined with F-6 it turns a
single "swap" into an arbitrary-length drain loop; on its own it means the contract's security
depends on a property of a vendored contract that our code neither checks nor documents, and that
a future app version or an ERC-777-style token hook could break.

**PoC:** `testAudit_F7_aSecondCallbackInsideOneSwapReverts` — two callbacks in one swap succeed
today.

**Recommended fix.** Consume the gate in the callback:

```solidity
function xycSwapCallback(...) external override {
    address expected = _activeApp;
    require(msg.sender == expected && app == expected, UnexpectedCallback(msg.sender, expected));
    _activeApp = address(0);            // one callback per swap, and it is this one
    IERC20(tokenIn).forceApprove(address(AQUA), amountIn);
    AQUA.push(maker, app, strategyHash, tokenIn, amountIn);
}
```

`swapExactIn` should then assert the gate *was* consumed (`require(_activeApp == address(0))`),
which additionally proves the app really did settle through us.

### F-8 — `swapExactIn` has no `deadline` {#f-8}

**Severity: Medium** (the checklist names it explicitly; the exposure is stale-price execution).

**Where:** `swapExactIn` L77-L84.

**Narrative.** A signed transaction that does not get mined stays valid. Without a deadline, a
visitor's swap can sit in the mempool (or in a bundler's queue, which for a sponsored UserOp is
someone else's queue) and execute minutes or hours later against a constant-product curve whose
reserves have moved. `amountOutMin` bounds the damage per swap, but a user who set a loose bound
for a small trade in a thin pool — which every rock's pool is — has no time bound at all. Every
router in production takes a deadline for this reason.

**No PoC test.** Writing it requires the parameter to exist; a test against an interface the
contract does not have would not compile. The test the hardening pass must add is:

```solidity
// test/audit/XYCSwapTakerAudit.t.sol
function testAudit_F8_aSwapPastItsDeadlineReverts() public {
    uint256 deadline = block.timestamp + 60;
    vm.warp(deadline + 1);
    try taker.swapExactIn(app, strategy, true, ONE_USDC, 0, address(this), deadline) {
        require(false, "a swap must not execute after its deadline");
    } catch { /* SwapExpired(deadline, block.timestamp) */ }
}
```

**Recommended fix.** Add `uint256 deadline` as the last parameter, with
`@param deadline Unix seconds; the swap reverts if it is mined later than this. Pass 0 for "no
deadline" only from a contract that has its own.` and
`error SwapExpired(uint256 deadline, uint256 nowTimestamp);`. The web encoder gets
`Math.floor(Date.now()/1000) + 300`.

### F-9 — The `expiresAt` boundary was self-consistent but unpinned {#f-9}

**Severity: Informational.**

**Where:** L405 (`expiresAt <= block.timestamp` rejects), L445 (`block.timestamp > h.expiresAt`
rejects), L542 (`getRock` downgrades on the same comparison), L622 (`att.deadline <
block.timestamp` rejects).

**Narrative.** All four comparisons agree: the deadline second is inclusive — a claim landing in
the block whose timestamp *equals* `expiresAt` succeeds, and `getRock` still reports
`HandoverPending` in that block. That is a defensible choice and it is uniform. It was simply not
tested and not spelled out, so a later "tidy the inequality" change would move it invisibly.

**PoC:** `testAudit_F9_aClaimAtExactlyExpiresAtStillSucceeds` — **this test passes today** and is
included as a regression pin, not as a failing proof.

**Recommended fix.** Keep the semantics; add one sentence to the `expiresAt` and `deadline`
`@param` text — "inclusive: `expiresAt` is the last second at which the gift can be claimed" — and
keep the test.

### F-10 — The claim relayer can be made to spend gas, and its rate limit fails open {#f-10}

**Severity: Medium** (operator cost; Sepolia-bounded today).

**Where:** `web/src/app/api/rocks/[id]/claim/route.ts:53` and `:77`;
`web/src/lib/rock-account.server.ts:170-213`; `web/src/lib/rate-limit.ts:54-57`.

**Narrative.** Three gaps compound.

1. **No pre-flight.** The route verifies the attestation's signature, rock id and deadline, then
   calls `sendTransaction` directly. It never asks the registry whether the rock is in
   `HandoverPending`, whether the caller is the named recipient, or whether the counter is fresh.
   Every one of those conditions fails *on-chain*, in a transaction the relayer pays for. One
   genuine attestation — which any person who taps any rock obtains for themselves — can therefore
   be posted repeatedly, each post costing a reverted transaction's gas.
2. **The rate limit fails open.** `consumeRateLimit` returns `{allowed: true, enforced: false}`
   when no D1 binding is present, and the route checks only `limit.allowed`. A misconfigured or
   unbound D1 turns the relayer into an unmetered faucet for gas. The repository's own D-017
   ("fail closed") is written for this case.
3. **Per IP only, and no budget.** The limit is 20/hour per client IP; there is no per-rock limit
   and no daily ceiling on relayer spend (`MAX_RELAYER_SPEND` or similar does not exist anywhere).

**Recommended fix.** Before broadcasting: `publicClient.simulateContract`/`estimateGas` on the
exact calldata and return the revert reason to the caller instead of paying for it; add a second
`consumeRateLimit(\`claim:rock:${id}\`, …)` bucket; refuse when `enforced === false` on this
spending route, exactly as the faucet does; and add a daily relayer budget from the environment,
or record in this file that its absence is an accepted Sepolia-only risk. The deeper
re-verification belongs to the perimeter audit (Part 3 step 4); it is recorded here because Part
1.2 lists it under Operations.

### F-11 — `deploy.js` accepts a zero attester and then validates it against itself {#f-11}

**Severity: Low.**

**Where:** `contracts/scripts/deploy.js:72-75` and `:122-129`.

**Narrative.** `isAddress("0x0000…0000")` is true, so a mistyped or unset-but-present

### F-21 — The attestation has no action field {#f-21}

**Severity: Informational.** The signed struct names *what* (rock, tag, counter) and *who*
(subject, smart account) but not *which call*. A signature minted for one attested function
satisfies the other wherever its field checks happen to pass: an awaken attestation
(`smartAccount != 0`) is a perfectly valid claim attestation for the same rock id, because
`claimHandover` ignores the field by design (D-026).

Today the impact is nil: `subject` is the same person in both cases, and an open handover is open
to whoever taps. It becomes real the moment a third attested action exists, or the verifier starts
signing attestations for a purpose other than claiming (a login proof, a visitor check-in). Adding
`bytes32 action` to the type — `keccak256("AWAKEN")` / `keccak256("CLAIM")` — is a one-field change
now and a migration later; it is worth doing while the type hash is still un-deployed.

### F-22 — A pause can strand a pending handover {#f-22}

**Severity: Informational.** `claimHandover` is `whenNotPaused` (L439) while the clock keeps
running. A pause spanning a handover's `expiresAt` kills that gift permanently: on unpause the
recipient's claim reverts `HandoverExpired` and the giver must initiate again. That is a defensible
reading of "pause admits no new ownership", and the checklist's requirement (pause must not stop an
owner *leaving* a state) is met. It should be stated in the `pause()` NatSpec so the operator knows
what a pause costs: "Pausing does not extend any pending handover; a gift whose expiry passes while
paused is dead and must be re-initiated."

### F-23 — `getRock` returns a nested struct {#f-23}

**Severity: Informational.** `getRock` returns `Handover memory` by value (L537), so adding any
field to `Handover` changes the return ABI and breaks every existing decoder — the web chain lib,
the MCP ABI copy and any Etherscan bookmark at once. Part 1.2 asks that a future field addition not
break the ABI. Either return the handover's fields flat (and keep the struct internal), or accept
and document it: "`Handover` is part of this contract's ABI; it will not gain fields."

### F-24 — No reentrancy guard, and unsupported token classes are undocumented {#f-24}

**Severity: Informational.** Two related gaps in `XYCSwapTaker`:

- `swapExactIn` has no reentrancy guard. Re-entering it from a token hook during the callback
  overwrites `_activeApp` and zeroes it on the inner return, which breaks the outer swap rather
  than stealing from it — self-denial, not theft — but the transient gate is meant to be a
  single-swap window and is not one. A `TransientLock` (already vendored, used by `AquaApp`) or an
  `require(_activeApp == address(0))` at entry makes it one.
- Fee-on-transfer, rebasing and hook-bearing tokens are unsupported in fact (a fee-on-transfer
  input leaves the periphery short and `AQUA.push` reverts) and unmentioned in the source. The
  checklist asks for the statement plus the note that the UI offers only USDC and WETH. Add it to
  the contract `@dev`, not only to `NOTES.md`.

### F-25 — `uint32` counter exhaustion is not documented {#f-25}

**Severity: Informational.** The NTAG's `SDMReadCtr` is 24 bits on the tag and `uint32` here, and
`_lastCounter` is monotonic for the life of the tag across archives. Exhaustion is unreachable in
practice (2³² taps) and the tag wraps long before this contract would. Part 1.2 asks for the
sentence; there isn't one. Add it to the `counter` `@param`: "Monotonic per tag for the life of
the registry; a `uint32` cannot be exhausted by a physical tag, which is read at most a few times
a minute."

  upstream). `reentrancy-benign` on `_activeApp = address(0)` after the external call is the

Neither tool finds F-1 through F-8. Every one of them is a semantic property of this system, which
is what the checklist and the PoC tests exist for.

---

## 6. Verdict {#verdict}

**Sepolia today: conditionally yes, and only as a demonstration.** Nothing in the registry can move
value, and on Sepolia the tokens the taker mishandles are worthless. F-1 is nevertheless a real
functional defect of the demo itself — the flow the project is built to show (give a rock away) ends
with the giver still able to retire the recipient's rock — so deploying without fixing it means
demonstrating a system whose central claim is false. F-11 is worth fixing before the deploy simply
because it wastes a deployment.

**A value-bearing network: no.** Not until F-1 (High) and F-5, F-6, F-7, F-8, F-2, F-3, F-10
(Medium) are fixed with regression tests, the three fuzz tests of F-13 exist, and a second reviewer
has re-checked each finding against the final source per Part 3 step 3. The Medium taker findings
compound: F-6 and F-7 together turn "the app is a parameter" into an arbitrary-length drain of
whatever the periphery holds, and F-5 guarantees that it sometimes holds something.

**One structural observation for the hardening pass.** F-1 exists because the registry stores an
authority (`smartAccount`) whose real controller changes off-chain, and F-6/F-7 exist because the
periphery treats a caller-supplied address as a trusted collaborator. Both are the same mistake in
two places: a trust boundary documented in prose rather than enforced in code. The prose in this
codebase is unusually good — it is how this review found most of these — but each of those comments
should end as a `require`.
